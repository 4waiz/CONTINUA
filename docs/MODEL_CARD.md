# Model card — CONTINUA link-violation predictor

**Version** `202609081132` · logistic regression · 13 features
**Artefact** `services/engine/continua_engine/models/predictor.json`
**Training report** `services/engine/continua_engine/models/training_report.json`

---

## 1. What it predicts

One binary question, asked every controller step about the path currently
carrying the session:

> Will this path violate an application threshold within the next **3 seconds**?

**Violation** (identical for the heuristic, the model and the offline labels —
`predictors.VIOLATION_DEFINITION`):

> smoothed RTT > **150 ms** (the control-class deadline), **or** windowed loss
> > **3.0 %**, **or** the path becomes unusable.

The horizon is configurable (`RunControl.horizon_s`, 0.5–15 s). Everything below
was measured at 3 s.

## 2. Intended use, and what it must not be used for

**Intended:** one input to a policy that decides whether to pre-warm and switch
to a backup path, inside this simulator.

**Not intended:**

* Any real network. It was trained on synthetic data from a model that does not
  include TCP congestion control, real radio behaviour or real traffic.
* Anything safety-critical. A missed warning here costs a simulated deadline.
* Being read as a probability — see §6.

**An LLM is not in this loop, and must not be.** Routing decisions are made by
this tabular model or the trend heuristic, both of which run in microseconds and
are fully inspectable. See `docs/AI_USE.md`.

## 3. Features

Thirteen, all observable at decision time:

`rtt_ms`, `rtt_slope_ms_per_s`, `jitter_ms`, `loss_pct`, `loss_slope_pct_per_s`,
`throughput_mbps`, `throughput_slope`, `queue_depth_bytes`, `coverage`,
`coverage_slope`, `speed_mps`, `rtt_over_deadline`, `alt_best_coverage`

Slopes are least-squares fits over a trailing 2 s window. `coverage` is
`modelled_coverage` — a geometric value from the world model, not a measurement;
in a real deployment this feature would have to be replaced by something
measurable, and the model retrained.

**No feature reads the future.** The prediction features are restricted to this
allow-list and a test enforces it.

### Largest weights (standardised)

| Feature | Weight |
| --- | --- |
| `coverage` | **−3.64** |
| `rtt_ms` / `rtt_over_deadline` | +1.03 each |
| `speed_mps` | −0.84 |
| `coverage_slope` | +0.62 |
| `jitter_ms` | +0.55 |

Falling coverage dominates, which is what one would expect and is also a warning:
much of the model's skill rests on a feature that is synthetic.

## 4. Training data

| | Block | Runs | Rows | Positive rate |
| --- | --- | --- | --- | --- |
| Train | `train` (base 10 000) | 35 | 15 350 | 0.574 |
| Tune | `tune` (base 40 000) | 20 | 8 085 | 0.539 |

* Generated by running the simulator under policy **P1** with the heuristic
  predictor, so the state distribution matches deployment.
* **Split by whole run and by scenario family, never by row.** Adjacent rows from
  one run are nearly identical; splitting on them leaks the answer.
* Scenario families **`outage` and `motion` were excluded from training entirely**
  and appear only in tuning, so the model is scored on shapes it never saw.
* Rows where the carrying path was **already violating** are dropped: predicting
  an ongoing condition is not forecasting.
* The **`test` block was never touched** by training or threshold selection.

## 5. Performance

On held-out tuning runs, at threshold 0.45 (chosen on tuning, never on test):

| | Precision | Recall | F1 |
| --- | --- | --- | --- |
| **Learned (logistic)** | **0.874** | **0.677** | **0.763** |
| Heuristic trend, same rows | 0.800 | 0.121 | 0.211 |

The heuristic is *precise but nearly deaf*: it catches about one violation in
eight. The learned model finds roughly two thirds of them at slightly better
precision. That is the honest case for it.

**False alarms are not free.** A switch made on a prediction where the incumbent
never actually violated is counted as an `unnecessary_handover` and appears in
the same experiment table as the wins.

## 6. Calibration — and why the score is not a probability

| | Value |
| --- | --- |
| Brier score | 0.1896 |
| Baseline (base-rate) Brier | 0.2485 |
| Mean absolute calibration error | **0.1364** |
| **`calibrated`** | **`false`** |

The model beats the base rate on Brier score, but its mean absolute calibration
error is 0.136 — a bucket of samples scored "0.7" contains roughly 57–83 %
positives. That is **not** good enough to call the output a probability, so the
artefact carries `calibrated: false`, the API forwards it, and the UI labels the
value "uncalibrated" wherever it appears.

Calibrating this properly (isotonic or Platt scaling on a separate split) is
future work. Until then the number is a **score**, and the project says so.

## 7. Fallback

`make_predictor("learned")` loads `predictor.json`. If the file is missing,
unreadable, or its feature list does not match `FEATURE_ORDER`, the learned
predictor reports itself unavailable and **the controller falls back to the
heuristic**. It never silently degrades into a predictor that always answers
"no violation", which would look like a working system while doing nothing.

`GET /api/health` reports `learned_predictor_available` so the fallback is
visible rather than silent.

## 8. Known limitations

* Trained entirely on synthetic data from this simulator. Transfer to a real
  network is **unevaluated and should be assumed poor**.
* The strongest feature, `coverage`, is a modelled geometric value with no real
  counterpart. A real deployment would need a measurable substitute.
* Linear model on 13 features: cannot represent interactions. A gradient-boosted
  tree was not attempted; it would need the same run-level splitting discipline.
* Only evaluated at a 3 s horizon.
* Class balance (~55 % positive) is an artefact of scenario mix, not a property
  of real networks.
* The tuning set includes the held-out families, so threshold selection saw them
  — but the *test* comparison did not, and no result in this repository is scored
  on tuning data.

## 9. Reproducing

```bash
PYTHONPATH=services/engine python -m continua_engine.controller.train_predictor --trials 5
```

Deterministic: the simulator is seeded, the split is by seed block, and
`scikit-learn`'s solver is deterministic for this configuration. Re-running
produces the same artefact apart from the timestamp in `version`.
